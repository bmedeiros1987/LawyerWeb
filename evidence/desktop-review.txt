Backup/restore consistency and durability review before commit:
- Backup takes database REPEATABLE READ snapshot, then reads files sequentially. Store lock covers cooperating app imports/restore/relocation, not external editors.
- Per-file size and mtime checks detect some writes while the open handle is read. They cannot guarantee a common-time snapshot across multiple files, detect path replacement after opening an inode, or rule out a write after the per-file check. Hash verifies archived bytes, not correspondence to a single external-editor state. Existing negative test covers appending during a read only.
- Backup fsyncs partial archive then renames it, but does not fsync parent directory. Power-loss durability of final name is not established.
- Restore verifies archive, writes temporary documents and renames them, then commits DB plus documents root atomically. Extracted files and directory entries are not fsynced before DB commit. A crash/power loss can leave DB committed without durable document bytes/names. DB rollback also leaves newly extracted files at the target.
- Existing target files with matching hashes are reused; an external editor can change them after check and before commit. No lock enforces editor quiescence. Safety backup is database-only; does not establish recovery of subsequently externally modified document copies.
These are remaining findings, not fixed or claimed safe here. No broad redesign performed. Need dedicated crash-injection and external-editor tests before claiming snapshot consistency or power-loss durability. Restrict validation to disposable stores.
